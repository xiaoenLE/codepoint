# 码点助手（CodePoint）

> 在**指定的编程软件**里，把中文输入法打出来的**全角标点自动换成英文半角标点**；
> 顺带提供**代码片段 Tab 补全**。纯 Python + tkinter，零第三方依赖。

写给谁用：用中文输入法写代码的人 —— PLC / ST（IEC 61131-3）、C、Python、Shell 都算。
中文输入法在中文标点模式下，`;` 会变成 `；`、`,` 会变成 `，`，写代码时每次都要切输入法
状态，很烦。这个工具把你指定的那几个程序"接管"掉：只要在那个程序里打字，
标点永远落在半角，输入法状态不用管。

---

## 1. 功能

| 功能 | 说明 |
|---|---|
| **标点自动转半角** | 中文标点 `，。；？！：""''（）【】《》` → `,.?!:;""''()[]<>`。只在你指定的程序里生效 |
| **快捷输入 / Tab 补全** | 配一条「检测字符串 → 补全内容」，比如敲 `if` 按 Tab 就补出 `IF … THEN … END_IF;` 骨架 |
| **补全内容里的变量** | 片段里写 `${datetime}` `${author}`，补全那一刻才换成真实时间 / 登录用户名 |
| **剪贴板净化** | 从别处复制来的中文标点，粘贴时换成半角（默认关，可在常规设置里打开） |
| **托盘 + 全局热键** | 默认 `Ctrl+Alt+A` 一键暂停 / 恢复；关窗口只收进托盘 |
| **开机自启** | 写当前用户的注册表 Run 键，不需要管理员权限 |
| **配置导入 / 导出** | 一整套规则存成一个 `.json` 带走，换电脑 / 给同事用；导入前先显示文件里有什么 |
| **重复启动 = 唤回窗口** | 窗口收进托盘后再双击一次程序，会把已有窗口显示出来（不会再甩一句"已经在运行了"） |
| **失效自愈** | 钩子被系统摘掉、修饰键状态卡住时**自己救回来**，不用重启程序（见 6.19） |
| **AI 补全（可选）** | 按 `Ctrl+Alt+G`（可改）：**选中了就改写**那段；**没选中就预测**接下来几行（自动抓光标前 N 行当上下文）。先弹窗给你看，Tab 插入 / Esc 放弃，窗上有倒计时自动关（见 4.5） |
| **预览窗可调外观** | 背景色 / 文字色 / 不透明度 / 字号 / 行数 / 宽度都能在设置里改，取色器直接点（见 4.6） |

三个开关随时可关：总开关（顶栏右上角）、标点替换、快捷输入。

程序列表默认有**「记事本」和「VS Code」**两条 —— 装好打开记事本敲个中文逗号，两三秒就能确认
功能生效没有。其它程序点主页的蓝色「+」，从"正在运行的程序"里挑即可。

## 2. 快速开始

### 2.1 环境要求

- **安装版**：Windows 10 / 11 x64，安装包内含运行环境。
- **源码运行**：Windows 10 / 11，Python 3.9+ 且带 tkinter（python.org 官方安装包默认带）。

先自检（不装钩子、不开界面，只验证环境）：

```bat
python main.py --selftest
```

输出示例：

```
== 码点助手 自检 ==
版本            : 1.0.4
Python          : 3.11.15  (...)
tkinter         : OK (Tk 8.6)
默认标点规则    : 24 条
默认快捷输入    : 9 条
配置目录        : C:\Users\<你>\AppData\Roaming\CodePoint
管理员权限      : 否（可能无法对提权程序生效）
消息线程        : OK
前台窗口探测    : code.exe · main.py
主板装配        : OK
== 自检结果: 通过 ==
```

### 2.2 启动

双击 `CodePoint-<版本>-Setup-x64.exe`，完成安装后从开始菜单打开 CodePoint。安装版将运行环境一次性解包到安装目录，之后直接启动。

升级前先从托盘退出旧版。新版默认读取原有的 `%APPDATA%\CodePoint` 配置。旧版已启用开机自启时，在新版中关闭再开启一次，就能把自启切到安装版。使用 `portable.flag` 的旧版可通过「常规设置」导出、导入配置。

从源码启动时使用下列命令。

```bat
run.bat                        :: 双击启动（自动挑一个带 tkinter 的 Python，无黑窗）
run.bat --console              :: 启动并保留控制台（排障用）
run.bat --where                :: 只打印它挑中的 python.exe，不启动
run.bat --selftest             :: 带参数的都自动走控制台，参数原样传给 main.py

python main.py                 :: 用自己的 python 启动
python main.py --minimized     :: 启动后直接进托盘
python main.py --headless      :: 无界面，只跑后台（排障用）
python main.py --config D:\cfg :: 指定配置目录（绿色版）
```

> **改 `run.bat` 前先看 6.6。** 它必须保持 **CRLF 换行 + 纯 ASCII**，
> 所以由 `python tools/make_bat.py` 生成，不要直接用编辑器改。

> **建议以管理员身份运行。** Windows 的 UIPI 限制下，非管理员进程无法把按键注入到
> 以管理员身份启动的程序。如果你的目标软件是提权运行的，标点替换会"看起来在工作
> 但目标程序收不到"。程序启动时也会提示这一点。

### 2.3 最短上手路径

1. 打开**程序列表**页 → 点蓝色 **+** → 从"正在运行的程序"里挑一个（不用手输进程名）；
   或者切到目标软件再点状态栏右侧的「**加入列表**」。
2. 回目标软件正常打字，中文标点自动变半角。
3. 想用快捷输入：敲 `if`，浮出提示条时按 <kbd>Tab</kbd>，补出完整骨架。
4. 想暂停：顶栏右上角开关，或按 <kbd>Ctrl</kbd>+<kbd>Alt</kbd>+<kbd>A</kbd>。

**"到底生效了没有"看程序列表页顶部那条状态栏** —— 它每秒刷新一次，直接告诉你
"当前程序 xxx.exe 已生效 / 未生效"，未生效时右侧还有「加入列表」按钮。

### 2.4 跑测试

```bat
python tests/run_tests.py -v      :: 单元测试（业务逻辑 + 界面静态检查）
python tools/live_check.py        :: 16 项真实按键注入验证，需要桌面会话
python tools/hook_health_check.py :: 13 项钩子探活 / 重挂 / 卡键复位的真机验证
python tools/hook_probe.py        :: 真手验证 Shift 组合符号的解析（20 秒）
python tools/ime_shift_probe.py   :: 真输入法验证"吞掉 Shift+符号 不会切中英文"（见 6.17）
python tools/ui_preview.py        :: 逐页截图到 build/preview，用来肉眼检查界面
python tools/quit_check.py        :: 跑一遍真主循环，测"托盘退出"干不干脆（约 50ms 为正常）
```

### 2.5 构建 Windows 安装包

构建机需要带 tkinter 的 Windows x64 Python、PyInstaller，以及 Inno Setup 6.3 或更新版本。`ISCC.exe` 在 `PATH` 内时可省略 `-Iscc`。

```powershell
python -m pip install PyInstaller
.\tools\build_installer.ps1 -Iscc 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe'
```

安装包位于 `dist\CodePoint-<版本>-Setup-x64.exe`，解包后的程序位于 `dist\fast\CodePoint`。如果需要原来的单文件便携版，运行 `python -m PyInstaller --noconfirm CodePoint.spec`。

## 3. 架构：怎么做到"高内聚 / 低耦合"

```
core/          纯数据 + 配置 + 跨层 DTO        ← 零依赖，不 import 任何其它层
services/      业务逻辑                        ← 只认 services/ports.py 的 Protocol
platform_win/  全部 Win32 / ctypes             ← 只认 core
ui/            tkinter 界面                    ← 只认 ui/ports.py
app.py         组装根：唯一做具体绑定的地方
```

**四条铁律**：

1. `core` 不依赖任何东西。
2. `services` **不 import platform_win、不 import ui** —— 需要的外部能力（注入按键、
   查前台窗口、查输入法状态、弹提示）全部走 `services/ports.py` 里声明的 Protocol，
   由 `app.py` 注入实现。
3. 所有 ctypes 声明只写在 `platform_win/winapi.py` 一个文件里。
4. `app.py` 是唯一写适配器的地方。

这个约束换来的收益很具体：**205 项单元测试全部在没有桌面、不按真键的环境下跑完**，
`tests/fakes.py` 用几十行就把"按键注入器 / 前台窗口 / 输入法 / 提示器"全替换掉了。

## 4. 配置

配置文件：`%APPDATA%\CodePoint\settings.json`（原子写 + 自动 `.bak` 备份，
损坏时自动备份为 `.corrupt` 并用默认值启动）。日志在 `logs\codepoint.log`。

绿色版：在程序目录放一个空的 `portable.flag` 文件，配置就改到 `程序目录\data\`。

### 导入 / 导出配置

「常规设置 → 配置备份」里有两个按钮：

- **导出…** 把当前这套配置（标点规则、快捷输入、程序列表、所有开关）存成一个 `.json`。
- **导入…** 整体替换现有配置。点之前会先解析文件、把"里面有多少条什么"显示出来，
  确认后才动手；替换前会自动把旧的 `settings.json` 备份成 `.bak`。

导入是**宽容**的：认得自己导出的文件，也认得**裸的 `settings.json`**
（直接把 `%APPDATA%\CodePoint` 里那个文件拷过来是最常见的用法）；
缺字段补默认值、多字段忽略，所以旧版本导出的文件导进新版本一定能用。
只有"根本不是配置文件"时才会拒绝，并给一句人话说明（比如 JSON 第几行错了）。

退出时**只在配置真的改过才回写** —— 否则会出现"我明明改了 settings.json，
程序一退出又被覆盖回去"的怪事。

### 生效范围

「程序列表」决定这个工具管哪些程序，有两种模式（常规设置里切）：

- **仅列表内的程序**（默认）：只有列表里的程序才生效，最安全。
- **所有程序**：任何程序都生效，列表变成"排除名单"（比如把微信加进去排除掉）。

### 关于 `:` → `:=`（默认停用）

「快捷输入」里有一条单字符规则：输入 `:` 补成 `:=`。它**默认是停用的**，
原因很简单：单字符触发会**永久劫持**那个字符 —— 冒号要靠 Shift+; 才打得出来，
启用后按冒号就永远变成 `:=`，CASE 标签 `0:`、变量声明 `x : INT;` 全都废了
（实测报障："只能打分号，冒号打不出来"）。

想要这个快捷输入：在「快捷输入」页把那条**勾上启用**即可，
代价是接受"受管程序里打不出单个冒号"。

> 这条规则在 v1 默认启用，v2（schema 版本 2）起默认停用；
> 旧配置会在下次启动时自动迁移，且**只迁移一次** —— 之后你在界面里
> 手动启用/停用都随你，不会被改回去。

### 只在中文标点状态下替换（更保守的选项）

默认**不管输入法状态，一律转半角** —— 因为"看起来没反应"比"多转了几个标点"更让人抓狂。

如果你经常在同一个窗口里写中文注释，可以打开「只在中文标点状态下替换」：
这时会去问输入法是不是真的在中文标点模式，只有是才动手；问不到就放行
（宁可不动，也不替你做错事）。

### 补全内容里的变量：自动填时间 / 作者

「补全内容」里可以写 `${变量}`，**补全那一刻**才替换成真实值 —— 所以注释头里的
时间永远是"插入的当下"，不是"写片段的那天"。编辑对话框里那排「插入变量」按钮
就是干这个的，点一下插到光标处，不用记名字。

| 变量 | 中文名也可以 | 结果 |
|---|---|---|
| `${datetime}` | `${日期时间}` `${现在}` | `2026-10-08 11:39:36` |
| `${date}` / `${time}` | `${日期}` / `${时间}` | `2026-10-08` / `11:39:36` |
| `${year}` `${month}` `${day}` | `${年}` `${月}` `${日}` | `2026` `10` `08` |
| `${hour}` `${minute}` `${second}` | `${时}` `${分}` `${秒}` | `11` `39` `36` |
| `${author}` | `${作者}` `${用户名}` | 系统登录用户名 |
| `${pc}` | `${计算机名}` `${电脑}` | 计算机名 |

英文名不区分大小写（`${Date}` 也行）。默认的 `///` 那条片段就是例子：

```
//==================================================
//内容: 
//作者: ${author}
//创建时间: ${datetime}
//==================================================
```

**两条安全规则**（很重要，因为 `${}` 在 JS / PHP 里也是合法语法）：

- **不认识的名字原样保留**：`${row.id}`、`${count}` 这类原封不动输出，
  你在 VS Code 里写 JS 模板字符串不会被吃掉。
- **想输出字面的 `${`，写成 `$$`**：`$${date}` 输出 `${date}`。

支持哪些变量在 `services/template.py` 的 `VARIABLES` 表里，加一行就多一个变量
（编辑对话框的按钮会自动跟着多一个）。

### 4.5 AI 补全（一个热键，两种用法）

按 `Ctrl+Alt+G`（可改），**选中了就改写，没选中就预测**：

| 按热键时有选区吗 | 它做什么 | 拿什么当输入 |
|---|---|---|
| **有** | 按需求生成代码，或提供所选代码的完整替换片段 | 选中的代码或自然语言需求 |
| **没有** | 补全：生成应插入在光标处的代码 | 光标前的 N 行（默认 6 行，最多 30）。启用 FIM 时也使用已取得的下文 |

两条路都是同一个交互：**光标旁弹预览 → Tab 插入 / Esc 放弃**。

预览里的长行会自动换行，内容较长时可用滚轮或翻页查看。预览高度只控制可见行数，模型达到输出上限时会提示重新补全。

#### 上下文怎么读取

标准 Windows 编辑框和支持 UI Automation 文本范围的编辑器，可直接读取已有选区或光标附近的代码。
开启 FIM 时，也会读取光标后的几行。读取过程不移动光标、不改变选区。

CODESYS / Invtmatic 等自绘编辑器如果没有可读的文本范围，会回退到 `Shift+↑/↓` 与复制。
已有选区直接用来改写。没有选区时才临时选择上下文，复制后保持 Shift 反向收缩到最初的光标位置。

「上下文行数」默认 6，可设为 0 到 30。设为 0 时仅使用选区。

## 6. 关键技术点与踩过的坑

这些都是实测踩出来的，写在这里省得下次再踩。

### 6.1 标点替换是怎么实现的

低级键盘钩子（`WH_KEYBOARD_LL`）→ 判断前台进程在不在生效范围 → 把按键翻译成
"它本来会打出什么字符"（`ToUnicodeEx`）→ 命中规则就**吞掉这个键**并注入半角字符。

三条安全策略：

1. **组字保护**：输入法正在拼字（候选列表开着）时绝不碰标点键 —— 很多输入法用
   `, . - =` 翻页选词，抢了就会打断选字。
2. **快捷键放行**：带 Ctrl/Alt/Win 的组合一律不处理。
3. **拿不准就放行**：任何异常都返回"不处理"，绝不把用户的键盘卡住。

吞键之后还有一步容易被忘掉的动作：**补一个无名键给输入法看**。
不补的话，输入法会把这次"只剩 Shift"的按键当成单击 Shift —— 也就是切换中英文
（详见 6.17）。

### 6.2 坑：同一个 `SendInput` 批次里连续相同按键会被当成"自动重复"

3 次退格打包进一个 `SendInput` 调用，实测只生效 0~1 次 —— Windows 把它们识别成
按住不放的自动重复。**改成"一次按键 = 一次 `SendInput`"后，连 0ms 间隔都 100% 生效。**
Unicode 文本注入（每个码元的 `wScan` 不同）可以安全合批。

### 6.3 坑：单字符补全必须吞掉触发键，否则退格会删错位置

单字符模式（敲 `:` 直接补成 `:=`）的三步是"注入字符 → 退格 → 写补全内容"。
如果**不吞**原来的 `:` 键：目标程序还没收到它，而我们的退格已经先执行了，
于是删掉的是**前一个**字符，位置全乱。用户看到的就是"按 `:` 结果 `:` 和 `:=` 乱跳"。
修法：单字符补全一律吞掉触发键，并把退格数减 1（那个字符根本没落地）。

### 6.4 坑：CapsLock 不能折算进标点键的 Shift 语义

`CapsLock` 只影响**字母**大小写，对标点键毫无影响。如果写代码时顺手把
"CapsLock 打开"当成"Shift 反向"，那么开着大写锁定时 `;` 会被算成 `:` ——
在受管程序里按 `;` 打出来的是 `:`（真的踩过）。所以 `_fallback_char` 里
字母才做 `shift != caps` 的异或，标点只认物理 Shift。

### 6.5 坑：纯 Python 画图时，圆角矩形每角只给 2 个点会画成月牙

tkinter 没有圆角矩形，常用"多点 + `smooth=True` 多边形"来近似。**每角只给 2 个点时**，
平滑样条会把弧线拉直甚至凹陷 —— 圆角小的时候看不出来，但画"完整胶囊"
（半径 = 高度一半，比如开关的底槽）会变成一个**月牙**，非常难看。每角给 5 个点就正常了。

### 6.6 坑：`.bat` 用 LF 换行会让 cmd.exe 把批处理拆散

双击 `run.bat` 后满屏 `不是内部或外部命令`，还有被拦腰截断的残渣（`cef PYEXE`）
—— 根因是 **cmd.exe 解析批处理要求 CRLF**。只有 `\n` 时，多行 `for (...)` / `if (...)`
块会被拆散，块内每一行被当成顶层命令执行；单行的 `set` / `echo` 反而不受影响，
所以症状是"一部分命令正常、一部分报错"，极易误判成路径写错。

**规矩**：`.bat` 必须 CRLF；只放 ASCII（中文 Windows 的代码页会让中文乱码）；
"自动挑解释器"这类逻辑用 `call :label` 子程序，别用跨行列表 + 嵌套括号。
本项目用 `python tools/make_bat.py` 生成，脚本里显式断言"裸 LF == 0 且非 ASCII == 0"。

### 6.7 坑：tkinter 控件的私有属性不能叫 `self._w` / `self._h`

`tkinter.Misc._w` 存的是控件的 **Tcl 路径名**。把它覆盖成自己的宽度/高度之后，
任何画布操作都会报 `invalid command name "44"`。自己的尺寸属性请叫
`self._width_px` / `self._card_w` 之类。

### 6.8 坑：`pack` 的顺序决定谁优先拿到空间

一行里"左边文字 + 右边开关"时，如果先 `pack` 左边的 `expand=True` 容器，
它会先把宽度吃掉，右边那个开关就被挤出可视区（截图上表现为"开关只剩半个"）。
**先 pack 右侧**，再 pack 左侧。

### 6.9 坑：tkinter 必须自己泵消息才会处理注入进来的按键

写验证脚本时，用 `time.sleep()` 干等再去读控件文本，读到的是**滞后**的内容，
会得出完全错误的结论。必须 `root.update()` 循环泵消息。

### 6.10 中文标点有两套，别只处理一套

- `。`（U+3002 表意句号）≠ `．`（U+FF0E 全角句点）；
- `、`（U+3001）、`《》`（U+300A/B）、`【】`（U+3010/1）都不在 `U+FF01–FF5E` 区间里。

逐键替换只用得上"可键入的 ASCII 标点"；**剪贴板净化**处理的是整段文本。

⚠ 第二套以前是靠 `text_conversion_map()` 里一句 `setdefault` 硬塞进转换表的 ——
结果是"规则页里根本没有这些条目，用户怎么关都关不掉"。把几十条规则全关了、
复制粘贴时 `。` 还是在变点（报障原话："关闭转换他还是转换"）。
现在**只认规则里 enabled 的条目**：表意标点默认不列，想转就在规则页自己加一条。

**刻意不转换表意空格 U+3000**：它常被用来做中文段落首行缩进，
换成半角会破坏排版，收益远小于风险。

### 6.11 坑：`theme` 常量写错一个名字 → 开关"一碰就消失、点了没反应"

界面里所有颜色都从 `theme` 取。这类拼写错误 Python 只在**真的执行到那一行**时才报，
于是出现了一种极难定位的故障：

```python
def _render(self, hover=False):
    self.delete("all")                                  # ← 先把画布清空了
    track = theme.SUCCESS_HOVER if hover else theme.SUCCESS   # ← 这里抛异常
```

后果有两层：**画布已经清空、异常却发生在绘制之前** → 鼠标一碰开关，
开关就变成一片空白；而且异常发生在 `self._command(...)` 之前 →
**点开关永远不生效**。用户看到的是"开关自己消失了，怎么点都没反应"。

两个修法都做了：

1. `_render` 改成**先把颜色全算出来，再 `delete("all")`** —— 万一以后再写错，
   控件只是不更新，不会变空白；
2. 加了一条静态检查（`tests/test_ui_widgets.py`）：扫遍所有 `theme.XXX` 引用，
   凡是没定义的直接让测试失败。这类 bug 代码里完全看不出来，只能靠机器扫。

### 6.12 坑：绝不在非界面线程里碰 tkinter（"托盘右键退出卡一下"）

托盘菜单、全局热键、第二次启动的实例，回调都跑在 **Win32 消息线程**上。
如果它们直接调 `root.destroy()` / `withdraw()`，会发现一个很阴险的现象：
**调用会"正常返回"（几毫秒），窗口却毫无反应**，实测能让进程一直卡着不退出。

规矩：`App.quit()` / `show_window()` / `hide_to_tray()` **只往事件桥投事件**，
由界面线程的轮询去执行（最多晚 30ms 生效）。这样任何线程调用都安全。

回归检查：`python tools/quit_check.py` 会真跑一遍主循环再触发托盘退出——
正常约 50ms，超过 1 秒就说明又有人在别的线程里碰界面了。

### 6.13 坑：`pathlib.write_text()` 会把 `\n` 悄悄换成 `\r\n`

Windows 上 Python 的文本模式默认做换行翻译，所以**批量改写脚本会把整个仓库**
从 LF 变成 CRLF。Python 不在乎，但它会让"按 LF 匹配"的编辑工具全部失效
（表现为"明明一模一样的代码，就是替换不上"），而且 `.bat` 又**必须**是 CRLF ——
两种换行混在一起最容易出事。

做批量文本改写时，用 `read_text()` + `write_bytes(text.replace('\r\n','\n').replace('\n','\r\n').encode())`
显式控制，别依赖默认行为。

### 6.14 坑：钩子线程里绝不能用 `GetKeyboardState` 解析字符（Shift 符号全废的根因）

`vk_to_char` 依赖 `ToUnicodeEx`，而 `ToUnicodeEx` 需要一份键盘状态数组。
图省事直接 `GetKeyboardState()` 的话——它返回的是**调用线程**的键盘状态，
在低级钩子回调里经常拿不到刚按下的 Shift。后果链条：

```
用户按 Shift+, → 钩子解析出 ','（Shift 丢了）→ 标点替换吞键 → 注入 ','
→ 用户看到的是 `,`，`<` 永远打不出来
```

受害者是**每一个"同键双字符"**：`,`/`<`、`.`/`>`、`;`/`:`、`'`/`"`、`/`/`?`……
用户实测报障原话："很多符号是需要 shift 结合的，< 和 , . >，都是，和；：一样，
都只能输出一个字符"。

修复（三件套，都在 `keyboard_hook.py`）：

1. **事件流跟踪**：钩子能看到每个键的按下/抬起，自己记一份 256 字节状态数组
   （修饰键只留按下位；CapsLock 只翻切换位，绝不折进 Shift——那是另一个修过的 bug）；
2. **`GetAsyncKeyState` 只补不减**：解析字符前拿物理异步状态**补漏**
   （流式说"没按"、物理说"按着"才置上），**绝不反向覆盖**——
   见下一节里的"回调滞后"场景，覆盖一次就把上档符号全废了；
3. 字符解析只喂这份自己维护的状态，**彻底不碰 `GetKeyboardState`**。

两个次生坑，都踩过：

- **通用键位 = 左右键位的"或"，且必须"先读齐再统一写"**。同步时如果按集合顺序
  一边读一边写，`VK_LSHIFT` 刚把 `VK_SHIFT` 置上，轮到 `VK_SHIFT` 自己又被
  异步状态里的"未按下"清掉——集合顺序不保证，bug 随机出现；
- **`GetKeyboardState` 的修饰字节带杂散位**（本机实测返回 `VK_SHIFT=0x01`），
  照抄会污染解析。种子状态里修饰键只认 `GetAsyncKeyState`，切换位只认
  `GetKeyboardState`（`GetAsyncKeyState` 的低位是"自上次调用以来按过没有"，
  不是切换状态）。

验证：`tests/test_shift_resolution.py`（四对符号 × 上档/下档、CapsLock 隔离、
漏事件自愈、回调滞后时 Shift 不被抹掉、key-up 自清）；真手验证用
`python tools/hook_probe.py` —— 它会打印钩子解析出的每个符号，`✓/✗` 一眼可见。

### 6.15 坑：业务回调（decide）绝不能握着钩子的锁 —— 一次死锁 = 全功能失效 + 退出卡顿

这是本项目**代价最大的一次故障**，而且两个症状看着毫无关系：

```
第一次标点替换之后，所有功能一起失效     ← 用户报障
右键退出要卡好几秒                      ← 同一件事的另一面
```

根因链条：

```
钩子回调（跑在消息线程）拿着 self._lock 调 decide
  → decide 里 SendInput 注入半角标点
  → SendInput 在**同一个调用栈**里把注入的按键重新喂回低级钩子
  → 同一线程二次进入 _hook_proc，第二次 acquire 同一个非可重入 Lock
  → 自己把自己锁死
```

卡住的是**消息线程**，而键盘钩子、托盘、热键、剪贴板通知全都寄生在它上面，
于是一次死锁 = 全功能失效；退出时 `App.shutdown()` 里的三个
`MessageWindow.call()` 各自干等超时，`join()` 也要等，于是"退出卡顿"。

两条修复 + 一条防御：

1. **decide 移到锁外**（`keyboard_hook.py`）。锁只保护状态数组和
   `_swallowed` 集合，绝不包住任何可能注入按键的动作；
2. **回调里的异常不许静默 `pass`** —— 这次故障难查，就是因为异常被吞得
   一点痕迹都没有，现在一律 `log.exception`；
3. `MessageWindow.call()` 的默认等待从 6 秒降到 2 秒，退出阶段 `App` 再压到
   1 秒 —— 即使将来又有地方卡住，退出也不会变成"点了没反应"。

**为什么单元测试抓不到**：单测和 `live_check.py` 都用假钩子直接调
`pipeline.handle`，走的是"决策对不对"，压根不经过真实回调的线程环境。
要复现必须让 decide 真的在消息线程里跑一次并注入 —— 这就是
`tools/diag_runtime.py` 干的事：手工构造 `KBDLLHOOKSTRUCT`（flags=0，
等价于真人按键），再用 `MessageWindow.call` 投到消息线程上执行。
回归测试在 `tests/test_hook_reentry.py`（重入不死锁、decide 期间锁可获取、
Lock 确实不可重入的反向验证、异常必须落日志）。

### 6.16 线程模型

```
主线程            tkinter 界面 + 事件泵（after 30ms 轮询 bridge）
Win32 消息线程    隐藏窗口 / 键盘钩子 / 热键 / 托盘 / 剪贴板通知
剪贴板 worker     剪贴板文本净化（避免阻塞消息线程拖慢钩子）
定时 ticker       快捷输入 pending 超时
```

**后台线程绝不直接碰控件**，只能往 `ui/bridge.py` 的队列里投事件；
界面线程用 `after()` 轮询。这是 tkinter 下唯一安全的做法。
连"退出程序 / 显示窗口 / 收进托盘"这三个动作也走事件桥 —— 它们全都可能
从托盘线程调用（见 6.12）。
（例外：`PhotoImage` 必须在界面线程创建，所以程序图标是"后台线程解析像素、
回到界面线程再 `PhotoImage(data=...)`"。）

### 6.17 坑：吞掉 Shift+符号 会把输入法切到英文（"每打一个冒号都跳英文"）

中文输入法（微软拼音默认就是）用「Shift 按下与抬起之间**有没有别的键**」来区分

```
单击 Shift        → 切换中英文
Shift + 别的键    → 组合键，什么都不切
```

而标点替换恰恰要把 `Shift+;` 那个键**吞掉**（才能把 `：` 换成 `:`）。
输入法于是在 Shift 抬起时看到的只剩一个孤零零的 Shift —— 判定为"单击",
中英文被切走。用户实测报障原话：

> 当 shift 用来切换中英文时，每次中文输入其他需要 shift 加其他按键时，
> 他会触发切换语言。这样也很不方便

受害者是**每一个 Shift 组合的符号**：`: < > ? " + _ { } | ~`……
更麻烦的是它**只在输入法内部发生** —— 我们自己的日志、统计、单元测试里
一点痕迹都没有，光看代码根本推不出来。

修法：**凡是吞掉了一个"按着 Shift 的键"，就补一个无名键**，让输入法看到
"Shift 之后还有别的键"：

```python
# services/pipeline.py
if swallow:
    self._guard_ime(key)      # → platform_win/input_simulator.send_ime_guard()
```

三个关键细节：

- **用 `0xE8`（Windows 未分配的虚拟键码）**：没有字符映射、没有默认消息处理，
  目标程序收到 `WM_KEYDOWN` 只会忽略。实测 `0xE8 / 0xFC / 0xFD / 0xFE / 0xFF`
  都有效，选了语义最轻的 `0xE8` —— `0xFE` 是 `VK_OEM_CLEAR`，个别老程序认它；
- **必须在 Shift 物理抬起之前发出去**：钩子在 `Shift+符号` 的 key-down 里就发，
  时序天然满足；而且要排在替换字符**前面**（同一批注入先发的先到）；
- **只对"吞键 + 按着 Shift"生效**：没按 Shift 的标点（`,` `.` `/`）不多发按键；
  带 Ctrl/Alt/Win 的组合本来就从不吞，所以也绝不会注入 `Alt+Shift+无名键` ——
  那正好是 Windows"切换输入语言"的热键，碰不得。

验证：`python tools/ime_shift_probe.py`（需要桌面会话 + 开着 Shift 切换中英文的
中文输入法）。它跑两段：① 纯合成按键验证输入法的判断规则；② 真钩子 + 真主板 +
真输入法的 A/B。本机实测输出：

```
== ② 代码级 A/B（真钩子 + 真主板 + 真输入法，走真实的 `;` 吞键链路）==
     不补守卫键（修之前）   文本=':'  守卫键×1  ★ 中英文被切走
     补守卫键（修之后）     文本=':'  守卫键×2  中英文没动
```

单元测试覆盖的是"**我们有没有补守卫键**"（`tests/test_ime_guard.py`，11 项：
吞 Shift 组合要补、没按 Shift 不补、快捷键场景不补、补失败也必须照吞不误）。

### 6.18 坑：ttk 的 `TButton` 自带默认宽度，小按钮会被撑成大方块

「插入变量」想在编辑对话框里摆一排小按钮（一行 6 个）。写完看着没问题，截图一看：

- 每个按钮**固定占 102px** —— 连只有一个字「年」的按钮也是 102px；
- 一行只放得下 4 个，第 5、6 个被容器裁掉，最后一个「计算机名」显示成「计」。

根因：`ttk.Button` 不写 `width` 时用的不是"文字自然宽度"，而是主题给的默认宽度。
量出来的对照（`tools/dialog_preview.py` 会打印控件尺寸）：

```
ttk.Button  不写 width      reqW=102
ttk.Button  width=0         reqW= 27   ← 按文字算
tk.Button  （经典控件）      reqW= 23
```

修法：在 `Bare.TButton` 样式里显式写 `width=0`。

**顺带一条**：这一排按钮还试过用 `grid()` 摆，结果列被 `fill="x"` 拉开、
超宽的那几个照样被裁。换成 `pack(side="left")` 逐行摆就老实了 —— 只按内容占位。

教训同上：**这类问题只读代码永远看不出来，必须截图 + 量尺寸。**

### 6.19 坑：偶发"能识别到程序、就是一个字都不转换"（要重启才好）

用户报障原话：

> 这个码点助手有点问题了，他不能正常转换了，可以检测到打开的应用，就是不能转换
>
> 他是有时候不可以，重新启动后又正常了

这类故障最难的地方在于**表面上一切正常**：前台程序识别到了、状态栏写着"已生效"、
开关也开着、托盘也在 —— 只有"按键不再经过我们"这一件事不对。根因有两处，
而且都必须能**自己救回来**（用户不该为了这个重启程序）：

#### ① 修饰键状态卡在按下 → 整个功能静默失效

钩子的修饰键状态靠**事件流记账**（6.14），可有些键盘事件我们**根本收不到** ——
最典型的是 UAC 提示框、Ctrl+Alt+Del、Win+L 锁屏这套**安全桌面**：
桌面一换，钩子就不被调用，用户在那上面松开的 Ctrl/Alt/Win/Shift 我们永远等不到 key-up。

卡住的后果不是"某个符号打错"，而是**所有按键一起失效**：

```
Ctrl 位卡在按下
  → platform_win/keylayout.vk_to_char 第一步就判断 "Ctrl 组合不产生字符" → 返回 None
  → key.char 是 None → services/punctuation 拿不到字符 → 所有按键原样放行
  → 界面、前台探测、托盘全都正常，就是一个字都不转换
  → 重启进程（状态数组重建）又好了
```

原来的 `_sync_modifiers_from_async` 只补不减（只补不减是**故意**的，见 6.14），
所以一旦卡住就永远卡住。现在分两条路线自愈：

| 对象 | 什么时候清 | 为什么可以这样 |
|---|---|---|
| Ctrl / Alt / Win | **每次按键**都跟 `GetAsyncKeyState` 对账，物理上没按就立刻清 | 它们只用来判断"是不是快捷键"，真按着的时候物理状态一定说按着，不存在"回调滞后导致误判" |
| Shift | 定时兜底：**卡住 ≥ 6 秒**且物理上没按才清 | Shift 决定 `:` 还是 `;`，必须信事件流 —— 直接按物理状态覆盖会毁掉全部上档符号（6.14） |

对账必须排在**解析字符之前**（`keyboard_hook._hook_proc` 的第 ②' 步），
否则挨的这一下自己就白挨了。

#### ② 钩子被系统摘掉 → 只能重启（以前）

Windows 对超时的低级钩子**静默移除**、不做任何通知，而且**没有任何 API 能查询
"钩子还在不在"**。唯一的办法是**发一个无害键看有没有人认领**：

```
services/hook_health.py  ── 每秒问一句（自带节流）
    ├─ 距上次回调 < 2.5 秒                  → 活着（正常打字中）
    ├─ 距上次探活 < 10 秒 / 用户没在动       → 跳过
    ├─ 前台不在生效范围内                    → 跳过（别去打扰别人的窗口）
    └─ 疑似掉线 → 注入一个 0xE8 探活
         ├─ 回调认领了 → 活着
         └─ 没人认领 → 就地重挂 + 复探确认（连续失败 3 次才放弃）
```

探活键用的是**输入法守卫键那个 0xE8**（Windows 未分配的虚拟键码，无字符、
无默认处理，实测寄存器/记事本/Tk 都无副作用，见 6.17），所以往焦点程序里
"敲"一下也不会留下任何东西。连续失败 3 次就停手（避免"重挂→失败→再探"变成探活风暴），
并把状态写到「关于 → 运行自检」里让你看得见。

#### ③ 顺手留下的现场证据

"重启就好"的故障最难查的就是**事后什么都没有**。所以：

- `PipelineStats.block_counts` 记下"本该能转换、却放行了"的原因计数
  （`not_in_rules` 不算 —— 它覆盖全部字母数字键，量级碾压其它原因）；
- 「关于」页多了「运行自检」卡片，直接摊开状态 / 钩子 / 没转换的原因；
- 主页状态栏下面会冒一行提示（平时空白、不占位置），只在规模化失败时出现；
- 自动重挂、清掉卡键都写 `logs\codepoint.log`，并弹一个托盘气泡告诉你。

#### 验证

`tests/test_hook_health.py`（36 项）。**有效性自检做过**：把 `_heal_command_modifiers()`
从回调里删掉后 `test_real_callback_heals_before_deciding` 立刻变红 ——
确认这条测试真的守得住回调接线，而不是摆设。

### 6.20 坑：AI 请求绝不能在钩子回调里等（会被系统摘钩子）

- **现象**（如果写挂）：接上真模型后，第一次生成要 1~2 秒。如果顺手在
  `pipeline._handle()` 里同步调 `completer.complete()`，那两秒里整个键盘钩子都在阻塞 ——
  Windows 的低层键盘钩子回调**超时（默认约 300ms）就会把这个钩子摘掉**，
  于是"用着用着突然什么都不生效了"，而且重启才好，看起来像玄学。
- **修法**：钩子线程只做三件事 —— 判定、`ThreadPoolExecutor.submit`、立刻返回。
  生成和注入都在后台线程。实测 Tab 的处理耗时 0.0~0.1ms（`tools/ai_selftest.py` 会打印）。
- **同时要有的两道护栏**（都有测试盯着）：
  - **按键护栏**：等待期间只要用户又敲了键（`engine.seq` 变了），结果直接丢弃 ——
    光标位置已经不可信，硬插就是插到错的地方。
  - **窗口护栏**：注入前再取一次前台 `hwnd`，和派发时不一致就丢弃 ——
    防止代码打进别的程序里。
- **另一个坑**：生成结果里的换行会被 `send_unicode_text` 转成 `VK_RETURN`，
  而编辑器收到回车会**自动缩进**。如果模型给的是"整体缩进一级"的代码，
  每行都会再被缩一次，越来越往右飘。所以清洗阶段必须剥掉公共前导缩进
  （`ai_provider.clean_code`，见 `tests/test_ai_provider.py::test_removes_common_indent`）。

### 6.21 坑：用 Ctrl+C 拿选中文本，等于动了用户的剪贴板

- **背景**：UIA 读不到 CODESYS 的正文（见 6.20 上面那条实测），
  所以"选中内容当提示词"只能走「替你按 Ctrl+C」。这是**唯一**通用手段，没有更干净的。
- **必须做备份-还原**：先 `get_text()` 存起来，复制完再 `set_text()` 写回。
  不还的话，用户按一下热键，剪贴板里刚复制的东西就没了 —— 这种"顺手弄丢别人东西"
  的 bug 比功能失效更招骂。
- **还原不了的情况要认**：只备份了文本。原来剪贴板是图片/截图时，
  `get_text()` 返回 None，此时**什么都不写**（硬写空串会让用户以为截图被吃了），
  只记一条日志。`GrabResult.restored` 会如实反映这一点。
- **怎么判断"到底选中没有"**：比内容不可靠（选中的可能和剪贴板里一样），
  所以用 `GetClipboardSequenceNumber()`。没选中 → Ctrl+C 不碰剪贴板 → 序号不变 →
  450ms 后超时 → 返回空。这个"超时"正好就是"你没选中东西"的判据，
  比先假设有再报错清楚得多。
- **一个必须成立的隐含依赖**：复制**不会取消选区**。正因为选区还在，
  注入的字符才会被编辑器当成"输入"来替换选区。哪天遇到某个编辑器复制后取消了选区，
  表现就是"代码插在选区后面而不是替换它" —— 那时得补救：注入前先发一次 Shift+Left
  或者干脆改成"插在后面"的语义。
- **验证**：`tests/test_ai_selection.py` 11 项（备份还原、超时、复制失败、
  原来是图片不还原、只按一次 Ctrl+C、修饰键没松不许按）。

### 6.22 坑：热键触发时 Ctrl/Alt 还按着，发出去的 Ctrl+C 其实是 Ctrl+Alt+C

这条是 v1.2.0 上线后**用户实测第一下就踩到**的：明明选中了三个字，按 `Ctrl+Alt+G`
却提示"没有拿到选中内容"。

- **现象**：选中文字 → 按热键 → 弹"没有拿到选中内容"。日志里每次热键之后都紧跟
  `清掉卡住的修饰键：0xA2（LCONTROL）` 和 `0xA4（LMENU）`。
- **根因**：`WM_HOTKEY` 是在**按下**那一刻触发的，此时 Ctrl 和 Alt **还实实在在按着**
  （用户还没来得及松手）。这时候 `SendInput` 发 Ctrl down + C down，系统看到的是
  **Ctrl+Alt+C** —— 记事本、CODESYS 都没有这个命令，剪贴板纹丝不动，
  450ms 后超时，于是报告"没拿到内容"。那个"卡住的修饰键"日志就是副作用：
  我们在物理键还按着的时候补了一次 down/up，钩子的事件流被搅乱了。
- **修法**：发 Ctrl+C 之前先 `wait_modifiers_released()` —— 用 `GetAsyncKeyState`
  轮询物理键状态（**不是**钩子的事件流，钩子在这种情况下不可信），等它松开；
  松手后再等 20ms 让目标程序处理完 key-up，然后才按键。
  一直不松手（超过 400ms）就**干脆不发**，直接提示"按完热键要松开 Ctrl 和 Alt"。
- 为什么不用 `WM_COPY` 直接给窗口发消息：不受修饰键影响，但自绘控件不保证处理它，
  通用性不如 Ctrl+C。留作以后的优化。
- **验证**：`GetAsyncKeyState` 读数正确性实机验证（按住 Ctrl → True，松开 → False，
  `wait_modifiers_released` 等到松手后 156ms 返回）；在真实记事本里跑完
  「输入 → Ctrl+A → 抓取」拿到 `HELLO_SELECTION_TEST`，耗时 46ms。

### 6.23 坑：Tab 要吞得干净，还得记得还回去

预览窗挂着的时候，Tab 是"接受"；没挂的时候，Tab 必须原样放行给编辑器做缩进。
两件事都错不得：

- **挂起时的检查必须排在 `_handle()` 最前面**。排在标点替换或快捷输入后面，
  就会出现"预览窗明明开着，按 Tab 却往编辑器里插了一个制表符"——那时前面的
  分支已经把按键处理掉了。
- **吞要吞干净**：挂起时哪怕内容已经作废（比如前台窗口换了），Tab 也必须吞掉 ——
  漏给编辑器就是一个多余的制表符，而且用户以为自己按了接受、其实什么都没发生。
  所以 `accept_pending()` 返回"插没插"，但 `_handle()` 一律 `return True`。
- **作废要果断**：挂起期间任何 key-down 都取消（除 Tab）—— 光标位置变了，
  插了就是插错地方。Esc 走同一条路：取消之后继续往下传，编辑器该干嘛干嘛。
- **模板补全和 AI 补全用同一块窗**，但**两个 pending 不能合并**：
  模板的 pending 在 `QuickActionEngine`（知道触发串多长、要退几格），
  AI 的 pending 在 `KeyboardPipeline`（只知道有段文字等着）。
  硬塞进一个状态机会把引擎那份干净的纯逻辑污染掉。
- **验证**：`tests/test_ai_provider.py::TestPipelineOffer` 11 项
  （没 Tab 不插、Tab 才插、打字作废、Esc 作废、切窗不插、关掉后 Tab 放行）。


## 7. 已知限制

1. **无法实时感知输入法的中英文状态**：输入法在英文态时，整词快捷补全仍会替换掉
   已输入的字符。
2. **需要管理员权限**才能对提权运行的目标程序生效（Windows UIPI 限制）。
3. **智能组字保护依赖 `ImmGetContext` 跨线程查询**，少数程序会返回失败，
   此时保守放行 —— 那段时间不做标点替换，但绝不会打断你选字。
4. **不是所有编辑器都暴露插入符位置**：Electron / 自绘界面的应用上，
   呼吸灯会退化为跟随鼠标。
5. **只处理文本剪贴板**，图片 / 富文本不动。

**修：打断一次之后，热键就再也用不了了**

- **根因是 Shift 卡在"按下"状态**。抓上下文要注入 `Shift+Up/Down`，`SendInput`

### v1.6.0

**AI 补全接入 FIM：让模型看见光标后面**

以前只把光标**前面**几行发给模型，它不知道后面已经写了什么。所以写到一半按热键时，
它经常自己另起一段、越写越偏。现在把后面几行也抓过去（suffix），模型只补中间缺的那段。

实测（`10_Map_yOutput[1..3]` 缺第 4 行，qwen2.5-coder:1.5b-base）：

| 策略 | 结果 |
|---|---|
| 只给上文 | 自己编出 `return result` 又新开一个函数，整段跑飞 |
| **带 suffix** | `10_Map_yOutput[4, 4] := y2张量输出;` —— 精准补上 |

- **两条路都实现了**，都走 `/v1/completions`：
  - `server`：请求里带 `suffix` 字段，服务端自己在 token 层套模板（1.3~1.7s）
  - `token`：客户端手拼 `<|fim_prefix|>…<|fim_suffix|>…`（1.1~1.3s，prompt 更短反而更快）
  - `auto`（默认）：先试 server，碰到 400/404/405 或**返回空正文**就自动换 token
- **按模型族选 token**：qwen / codegemma 一套，deepseek-coder 一套（`<fim_begin>`），
  codellama / starcoder 另一套。选错了**不报错**，只会补出空行 —— 所以留了手动指定。
- **抓 suffix 靠键盘**（UIA 读不到 CODESYS 的正文）：`Shift+Down × N → Ctrl+C → Left`。
  取消选区必须按 **Left** —— 向下选出来的选区，左端才是原光标；向上选才按 Right。
  端反了光标会跑到文件后面，用户接着打字就打错地方，而且想不到是补全工具干的。
- **上下文按字符裁剪**（新增 `ai_prefix_max_chars` 1200 / `ai_suffix_max_chars` 600）：
  光限行数不够，一行超长的 IO 映射能把 6 行撑到几千字符，prefill 明显变慢。
  两个方向都朝光标收敛 —— 上文留尾部、下文留头部，离光标越远的越没用。
- **生成量不再跟预览窗显示行数绑定**。以前拿 `ai_card_max_lines` 当生成上限，
  还套了 `min(8, ...)`，等于自己掐自己。现在显示归显示（超出折叠成「… 还有 N 行」），
  生成归 `ai_max_tokens`，只留 24 行安全阀防跑飞。同一用例实测从 8 行变 16 行。
  代价是慢：400 tokens 全用满要 15 秒，靠流式预览边生成边看。
- **流式**：`/v1/completions` 的增量在 `choices[0].text`，**不在** `delta.content` ——
  少认这个字段流式就永远是空的。推给界面的还是剪过重叠的最终形态，看到的就是会插入的。
- 设置页新增「FIM 补全（顺便看光标后面）」一节：开关 / 请求方式 / token 格式 / 抓下文行数。
- 新增 `tools/fim_selftest.py`：一条命令判断某个服务到底支不支持 FIM。
  FIM 的失败几乎都是静默的，有这个能快速分清是模型的问题还是配置的问题。
- 新增 38 个测试（`tests/test_ai_fim.py`），全量 409 个通过。

**标点表清理 + 关掉的规则真的生效**

### v1.5.4

**AI 补全能"接着写一整组"了：规律在代码里算，不指望模型猜**

- **问题**：写 IO 映射时（`IO_Map.yOutput[1, 0] := y2报警输出;` … `[1, 7]`）按热键，
  1.5b 会把第二维续成 `[1, 8]`…`[1, 15]`，1.3b 干脆把 8 行原样抄回来 —— 模型看不出
  "0..7 是一组、该换下一轴了"。
- **做法**：新增 `index_pattern_hint()` / `index_pattern_seed()`，先算清楚再喂给模型：
  认出"第一维固定、第二维排满 0..7"的组，直接告诉它下一组是 `[2, 0]`、
  名字里的数字该从 2 改成 3（轴号与名字的差值按上下文推，不是无脑 +1），
  并把下一组的第一行算出来当样板。
- **一维同样支持**：`yOutput[0] := y1;` / `yOutput[1] := y2;` 这种只有两行时也认，
  接着写 `[2] := y3`、`[3] := y4`…
- **光标锚定**：规律必须紧贴光标（上下文最后一行属于该组）。光标已经移到别处时
  不再乱补。例如上面写完 4 行赋值、下面又写了 `1 2 3 4`，这时接的是 `5 6 7 8`，
  不会再回头补 `yOutput[4]`。
- **纯编号序列直接算**：`1/2/3/4` → `5 6 7 8…`，不调模型（0.00s）。
- **行数与内容兜底**：`max_lines` 在输出端硬截断（实测 0.5b 会一口气写 24 行）；
  认出规律时丢掉串场的行（模型偶尔吐裸数字或别的数组），并把 `[2] = y3` 的
  冒号补回 `:=`。
- 实测（qwen2.5-coder）：`[1,7] → [2,0]` 整组 8 行 3/3 命中，0.5b 3 秒、1.5b 8 秒；

### v1.0.2

**修复：编辑多行内容时，按回车会被当成"确认"，一下回车就退出编辑**

- **现象**：在「快捷输入」里编辑/新增一条规则，光标在「补全内容」多行框里打代码，
  敲一次回车想换行 —— 结果对话框直接确认关闭，多行内容根本写不进去。
- **根因**：``ModalBase`` 把回车确认绑在了 **Toplevel** 上
  （``self.bind("<Return>", ...)``）。Tk 会把 Toplevel 塞进**每个子控件的 bindtags 链**
  尾部 —— 实测多行 ``Text`` 的 bindtags 是

  都会一路冒泡到 Toplevel 触发确认，包括本来就该换行的多行 ``Text``。
- **修法**：带多行输入的对话框**彻底不在 Toplevel 上绑回车**，只把「回车 = 确认」绑到
  **单行 Entry** 上（回调 ``return "break"`` 吃掉事件）。多行框里回车就交给 Tk 的
  ``Text`` 类绑定插入换行。只有**没有多行框**的纯确认框（``ask_confirm`` /
  ``show_message``）才在 Toplevel 上保留回车确认，那边不存在换行冲突。
- **踩坑记录**：这条 bug 第一次"修"时用了 ``event_generate`` 驱动的 UI 测试，但
  **未映射/未获焦的控件上 ``event_generate`` 根本不派发事件**（实测所有回调计数为 0），
  测试假绿、真机照旧。现在改测**绑定表本身**（bindtags + ``bind("<Return>")``），
  并把"bindtags 里确实含 Toplevel"这条因果也钉进测试；同时用真窗口 + 真 ``SendInput``
